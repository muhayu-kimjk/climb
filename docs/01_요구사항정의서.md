## 이 문서 읽는 법

각 요구사항 앞의 표시는 결정 상태를 뜻합니다.

- **[확정]** 기획자가 직접 결정한 사항
- **[가정]** 아직 정하지 않아 업계 일반 관행으로 임시로 정한 기본안. 기획자 검토 후 바뀔 수 있음
- **[제안]** 컴플라이언스, 운영 관점에서 추가를 권하는 사항. 기획자 승인 전까지는 범위 밖
- **[미정]** 결정이 필요한 사항
- **[제외]** 검토했지만 넣지 않기로 한 사항 (기록을 남기려고 지우지 않음)

요구사항 ID는 `REQ-영역-번호` 형식입니다. 프로토타입 HTML 코드의 주석에도 같은 ID를 적어, 화면, 기능이 어떤 요구사항에서 나왔는지 추적할 수 있게 합니다.

panda 초안에서 가져온 요구사항에는 **(panda p.쪽)**으로 출처를 적었습니다. 초안 내용은 지금 다시 확정한 것이 아니므로 대부분 [가정]으로 두었습니다.

## 1. 프로젝트 개요

### 1.1 배경

현재 계약 관련 정보가 세 곳에 흩어져 있습니다.

- 내부 CRM: 계약 이력만 기록
- 내부 전자문서결재 플랫폼: 결재 문서
- 계약서 파일: 별도 보관

CLIMB은 계약 등록부터 내부 검토와 결재, 체결본 보관, 사후관리, 갱신과 만료까지를 한 곳에서 관리하는 것을 목표로 합니다.

**목표 (panda p.3)**

- 영업 활동 단계를 세부적으로 나눠 **계약 관리, 인감 관리, 운영 관리**로 분리합니다.
- 내부통제 요소를 단계마다 녹여, 최소한의 **내부회계관리제도** 준수를 이끌어 냅니다.

### 1.5 CPQ와 CLM 범위 (REQ-SCOPE)

CLIMB은 계약 관리(CLM) 시스템이라고 부르지만, 실제로는 견적과 가격 통제(CPQ) 기능도 함께 가집니다.

| 구분 | 뜻 | CLIMB에서 다루는 것 |
|---|---|---|
| **CPQ** (Configure, Price, Quote) | 제품 구성, 가격 책정, 견적 | 제품별 구성과 금액, 서비스 기간, 표준단가표 적용 여부, 할인율 한도(cap) 준수 여부, 최종 견적서 |
| **CLM** (Contract Lifecycle Management) | 계약 생애주기 관리 | 계약서 작성, 검토와 결재, 인장 날인과 체결, 보관, 운영 적용, 변경과 갱신, 종결 |

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-SCOPE-01 | 확정 | CLIMB은 **CPQ와 CLM 기능을 함께** 가집니다. 요구사항과 화면은 두 기능을 모두 고려해 만듭니다. |
| REQ-SCOPE-02 | 확정 | 가격 기준인 **표준단가표와 할인율 한도를 시스템에 저장**하되, 정해진 사람만 볼 수 있게 열람을 제한합니다. (C-13 해결. panda 초안은 영업만 알게 하는 방식이었음) [가정] 볼 수 있는 사람은 영업, 세일즈어드민, 관리자이고, 가격 기준은 관리자가 관리합니다. 계약 등록 때 제품별 금액을 넣으면 할인율과 한도 준수 여부가 자동으로 계산되어 체크리스트 2, 3번이 채워지고, 영업은 비고만 적습니다. |
| REQ-SCOPE-03 | 확정 | 영업 접수, 영업 기회, 영업 활동 관리는 지금처럼 기존 CRM에서 합니다. (REQ-FLOW-01, panda p.4, p.6) [가정] 계약을 등록할 때 CRM의 영업 기회 번호를 연결해 둡니다. |

**색 사용 기준 (REQ-UI-05) [가정]**

- 무하유 Green 바탕 위에 흰 글자를 쓰면 대비가 2.4:1로 기준에 못 미칩니다. 그래서 **초록 버튼의 글자는 Black**(대비 7.6:1)으로 합니다.
- 초록 계열 글자가 필요하면 Dark Green을 씁니다.
- 보조 설명 글자는 Black을 72% 농도로 쓴 회색(`#49595F`, 대비 7.3:1)을 씁니다. Gray(`#8F8F9B`)는 글자에 쓰지 않습니다.
- Pink를 바탕으로 칠한 곳(반려 배지, D-30 배지, 결재 지연 표시, 반려와 승인 취소 확인 버튼)은 진한 핑크(`#DC237F`) 바탕 + 흰 글자로 합니다. (REQ-UI-09)
- 반려 건 표 줄처럼 아주 연한 분홍을 깐 곳은 흰 글자가 보이지 않으므로 Black 글자를 그대로 씁니다.
- 나머지 상태 배지는 "연한 바탕 + 브랜드 색 테두리 + Black 글자"로 통일합니다.

> - 시스템 서버는 사내망, VPN 대역에서 오는 접속만 받도록 제한하는 것을 가정합니다.

### 2.1 보안 요구사항 (REQ-SEC)

CLIMB을 ISMS-P 인증기준에 맞게 설계하기 위한 요구사항입니다(v0.22). 기획자가 정한 항목은 확정, 기본안으로 둔 항목은 가정입니다. 괄호 안은 근거입니다.

- 인증기준: 「정보보호 및 개인정보보호 관리체계 인증 등에 관한 고시」 별표 7 (2024-07-24 발령본, 2026-10-20 원문 확인)
- 안전성 기준: 「개인정보의 안전성 확보조치 기준」 개인정보보호위원회 고시 (2026-07-01 발령본, 2026-10-20 원문 확인)

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-SEC-01 | 확정 | **목표:** ISMS-P 인증기준을 충족하도록 설계합니다. 회사 ISMS 인증은 제품 대상이라 CLIMB은 범위 밖이지만, CLIMB만으로도 ISMS-P를 받을 수 있는 모범 사례로 만듭니다. 개인정보는 안전성 기준을 함께 지킵니다. 실무를 지나치게 불편하게 하는 항목은 기획자와 정합니다. |

> **개발팀 참고 (REQ-SEC)**
> - 워터마크는 유출을 억제하고 추적하는 장치이며 캡처를 막지는 못합니다. 내려받는 PDF와 미리보기는 서버가 워터마크를 찍어야 합니다. 프로토타입은 인쇄할 때만 보이는 워터마크를 `common.js`의 `renderWatermark`와 `common.css`의 `.watermark`로 시연합니다.
> - 2단계 인증 여부는 로그인 정보만으로 확인하기 어려울 수 있으므로, 회사 Google Workspace 관리 콘솔에서 2단계 인증을 강제하는 방식을 가정합니다(IT팀 확인 필요).
> - 기록은 덧붙이기만 되는 저장소(수정, 삭제 불가)에 두고, 서버 시각은 표준시로 맞춥니다(인증기준 2.9.6).
> - 관리자 기능의 사내망 제한과 권한 검사는 화면이 아니라 서버에서 접속 주소와 역할로 검사합니다.

## 3. 업무 범위와 계약 처리 흐름 (REQ-FLOW)

### 3.1 범위

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-FLOW-01 | 확정 | 관리 대상은 자사 SaaS 서비스 관련 계약입니다. 영업 기회(파이프라인) 관리는 기존 CRM에서 계속하며 CLIMB 범위에 포함하지 않습니다. |
| REQ-FLOW-02 | 확정 | 시스템 도입 이후 새로 발생하는 계약만 관리합니다. 기존 계약은 옮기지 않습니다. |

### 3.2 업무 흐름 5단계와 세부 단계

CLIMB의 업무 흐름은 5단계이고, 각 단계 안에서 panda 초안의 세부 단계(①~⑪)를 거칩니다. (panda p.4, p.34~37) v0.13에서 4단계 "보관함"을 **운영 검토**와 **계약 완료**로 나눴습니다.

```
 [1단계] 계약 등록 (영업)
    ① 계약품의 작성: 계약 내용 + 체크리스트(표준계약서, 표준단가표, 할인율 한도) → 기안
       ※ 임시 저장, 계약서 초안 첨부, 열람 제한 여부 체크
      │
      ▼
 [2단계] 계약 검토 ◀────────── 반려되면 기안자(영업)에게 돌아가 보완 후 재기안
    ② 체크리스트 검토 (세일즈어드민) ──── 항상
    ③ 영업 검토 (영업 리더, 리더 본인 건은 영업 담당 임원) ── 가격 조건이 기준을 벗어날 때
    ④ 법무 검토 (법무) ──────────────── 표준계약서를 쓰지 않을 때
    ⑤ 개인정보 검토 (개인정보 담당) ───── 개인정보를 처리할 때 [CLIMB 추가]
       ※ 순서: ② 다음 ③, 그 다음 ④와 ⑤를 동시에 (REQ-STEP-04, v0.20에서 바뀜)
      │
      ▼ 승인
 [3단계] 계약 체결
    ⑥ 인장 날인 검토 (총무): 기초 정보 일치 확인, 인장 날인, 인장 사용 기록
    ⑦ 상대방 서명 (영업, 시스템 밖) → 체결본 등록
    ⑧ 체결본 확인 (세일즈어드민): 승인된 내용과 같은지 확인
      │
      ▼
 [4단계] 운영 검토
    ⑨ 운영 적용 (CEM): 서비스 라이선스나 도메인을 열고 계약 정보 설정
    ⑩ 재무 확인 (재무기획): 회계 인식 [가정: 운영 검토 단계에 둠]
      │
      ▼
 [5단계] 계약 완료 (실제로는 보관함)
    ⑪ 계약 종결: 계약완료 기록으로 차곡차곡 쌓임, 이후 사후관리
      └─ 변경, 갱신은 3.8 계약 변경 절차로 처리 (원계약에 연결)
```

### 3.3 여러 해 이어지는 계약의 관리 원칙

수년간 이어지는 계약을 한 건으로 볼지, 별건으로 볼지에 대한 원칙입니다. **방식 C와 세부 원칙을 모두 채택했습니다.** (C-07 해결)

| 방식 | 내용 | 내부통제 관점 |
|---|---|---|
| A. 한 건에 덮어쓰기 | 갱신, 변경 때 기존 계약 정보를 고쳐 씀 | 추천하지 않음. 이전 조건과 승인 근거가 사라져 감사 추적이 끊김 |
| B. 모두 별건 | 갱신, 변경마다 완전히 새 계약으로 등록하고 서로 연결하지 않음 | 승인 기록은 남지만, 한 거래처와 이어지는 계약 이력을 한눈에 보기 어려움 |
| **C. 묶음 + 차수별 별건 결재 (추천)** | 원계약을 기준으로 묶고, 갱신과 변경은 각각 별건으로 기안, 결재, 체결본 등록 | 건마다 승인 근거가 남고, 묶음으로 전체 이력도 추적할 수 있음 |

방식 C의 세부 원칙:

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-FLOW-18 | 확정 | **묶음 번호:** 원계약 번호를 묶음 번호로 쓰고 차수를 붙입니다. 변경은 `-A01, -A02`, 갱신은 `-R01, -R02` 예: `CT-2026-0105` → `CT-2026-0105-A01`(1차 변경), `CT-2026-0105-R01`(1차 갱신) |

> **개발팀 참고 (REQ-REG-06, 07, 09)**
> - 체크리스트 2, 3번 계산과 결재선 결정은 화면에서 미리 보여 주는 것이고, 화면 값은 사용자가 바꿀 수 있으므로 **서버에서 가격 기준으로 다시 계산해 검증**해야 합니다.
> - 할인율 = (표준 단가 x 수량 - 계약 금액) / (표준 단가 x 수량). 2번은 할인한 제품이 하나라도 있으면 "아니오", 3번은 할인율이 그 제품의 한도를 넘는 제품이 하나라도 있으면 "아니오"입니다.
> - 프로토타입의 가격 기준 값(`mock-data.js`의 `PRICE_BOOK`: 제품 코드, 표준 단가, 할인율 한도)은 화면 시연용 **가상 값**입니다. 실제 값은 관리자가 "가격 기준 관리"(SCR-54)에서 넣습니다.
> - 계약번호 일련번호는 서버에서 기안 순서대로 부여해야 하며, 화면의 번호는 예시입니다.

#### 3.6.1 내부회계관리제도 관점 검토 (v0.20)

영업 검토(할인 승인)를 법무 검토 앞으로 옮기면서, 내부회계관리제도가 매출 과정에 기대하는 통제와 CLIMB을 맞춰 보았습니다.

**의무 대상인지** (2026-10-20 현행 법령 원문 확인)

- 「주식회사 등의 외부감사에 관한 법률」 제8조 제1항: 회사는 내부회계관리규정과 이를 관리, 운영하는 조직(내부회계관리제도)을 갖춰야 합니다. 다만 주권상장법인이 아닌 회사로서 직전 사업연도 말 자산총액이 1천억원 미만인 회사는 제외합니다.
- 같은 법 시행령 제9조 제1항: 유한회사, 직전 사업연도 말 자산총액이 5천억원 미만인 회사 등도 제외합니다. 다만 주권상장법인, 공시대상기업집단 소속 국내 회사, 사업보고서 제출대상법인, 금융회사는 5천억원 미만이어도 대상입니다.
- **무하유는 의무 대상입니다**(v0.21 기획자 확인). IPO를 준비하며 K-IFRS 전환을 마쳤으므로 CLIMB은 **상장사 기준**으로 설계합니다. 상장 뒤에는 감사인이 내부회계관리제도를 감사합니다(같은 법 제8조 제6항 단서, 자산총액 1천억원 미만 상장법인은 검토). CLIMB은 매출 과정에 쓰이는 시스템이라 점검 대상이 될 수 있으므로, 시스템 자체의 통제(접근 권한 관리, 프로그램 변경 관리, 기록)도 갖춥니다(REQ-ENV-13).

**순서에 대한 판단**

- 내부회계관리제도는 법무 검토와 영업 승인의 순서를 정해 주지 않습니다. 법무 검토는 법적 위험을 보는 통제이고, 할인 승인은 매출 금액이 맞는지와 관련된 통제입니다.
- 할인 승인은 "고객에게 가격을 약속하거나 계약을 체결하기 전에 권한 있는 사람이 승인한다"는 사전 승인 원칙에 따라 가능한 한 앞에 둡니다(REQ-STEP-04).
- 견적서를 내기 전에 할인을 승인받는 것이 가장 바람직하지만, 견적 발급은 통제하기 어려워 **하지 않기로 했습니다**(v0.21 기획자 결정). 계약 단계의 ③ 영업 검토가 할인 승인 통제입니다. 견적에서 이미 제시한 할인이 영업 검토에서 반려될 수 있다는 위험은 남습니다.

| 직무 분리 | 가격을 정하는 사람, 승인하는 사람, 가격 기준을 바꾸는 사람이 서로 다름 | 영업이 정하고 부서장이 승인하며, 리더 본인 건은 임원이 승인. 가격 기준 변경은 사내 품의 결재로 승인받고, 관리자가 품의 문서 링크와 함께 바꾸며 이력을 남김(v0.21) | REQ-STEP-02, REQ-CHK-07 |

#### 3.7.1 결재 화면 동작 (REQ-REV)

1단계 결재 화면(SCR-20~23)을 만들며 정한 동작입니다(v0.18). 대부분 [가정]이며 시안을 보고 바꿀 수 있습니다.

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-REV-01 | 가정 | **검토 대기(SCR-21):** 내 차례인 결재 단계를 오래 기다린 순서로 보여 줍니다. 칸은 고객사(계약번호), 서비스, 단계, 요청자, 기안일, 대기 일수입니다. 한 단계에 5일 이상 머문 건은 대기 일수를 진한 핑크로 강조하고, ④와 ⑤가 동시에 차례면 "동시: ⑤"처럼 알려 줍니다. 검색과 단계, 서비스, 대기 기간으로 거릅니다. 슈퍼관리자와 관리자는 모든 담당자의 차례를 담당자 칸과 함께 봅니다. |
| REQ-REV-02 | 가정 | **검토 상세(SCR-23):** 계약 한 건을 하나의 결재 문서처럼 보여 줍니다(REQ-DOC-01). 순서: 제목(고객사)과 계약번호, 서비스, 구분, 기안 차수, 상태 → 내 차례 안내 → 결재란 → 기본 정보 → 금액과 제품(제품별 수량, 표준 금액, 계약 금액, 할인율과 총액. 할인율 칸은 "표준 단가" 또는 "N% 할인"만 보여 주고, 할인율 한도 값은 보여 주지 않음. 한도를 지켰는지는 체크리스트 3번에서 봄, v0.19) → 체크리스트(답, 비고, 그 답으로 거치거나 생략한 단계) → 첨부 파일과 검토 요청 사항 → 결재 기록. |
| REQ-REV-03 | 가정 | **결재란:** 칸은 ① 기안과 계약 검토 단계 ②~⑤입니다. 칸마다 담당 역할과 이름, 결과(승인, 차례, 대기, 반려, 생략), 일시(차례면 며칠째, 생략이면 까닭)를 적습니다. 생략한 단계도 칸을 두고 흐리게 보여, 왜 거치지 않았는지 알 수 있게 합니다(REQ-DOC-02). |
| REQ-REV-04 | 가정 | **처리 막대:** 내 차례인 단계가 있으면 화면 아래에 붙은 처리 막대에 반려와 승인 버튼을 둡니다. 휴대폰에서도 같은 막대가 화면 아래에 붙어 한 손으로 누를 수 있습니다(REQ-ENV-06). 버튼을 누르면 확인 창이 열리고, 승인은 의견 선택, 반려는 사유 필수입니다(REQ-DOC-07). 확인 창에는 처리하면 어떻게 되는지만 한 줄로 적습니다(v0.19): 승인은 "다음 단계로 넘어갑니다", 반려는 "기안자에게 돌아가고, 기안자가 보완해 다음 차수로 다시 기안합니다", 승인 취소는 "이 단계는 다시 내 차례가 되고, 승인과 취소 기록은 모두 남습니다". 반려와 승인 취소는 신중하게 누르도록 확인 버튼을 진한 핑크로, 승인은 초록으로 합니다(REQ-UI-09). 처리하면 그 결과와 다음 차례를 안내합니다. |
| REQ-REV-05 | 가정 | **승인 취소:** 내가 승인한 단계를 다음 단계가 아직 처리하지 않았으면 처리 막대에 "승인 취소"가 보입니다. 취소 사유를 적어야 하고, 취소하면 그 단계는 다시 내 차례가 되며 뒤 단계는 대기로 돌아갑니다. 승인과 취소 기록은 모두 남습니다(REQ-DOC-06). |
| REQ-REV-06 | 가정 | **검토 완료(SCR-22):** 내가 한 결재(승인, 반려, 승인 취소)를 최근 것부터 보여 줍니다. 칸은 처리일시, 고객사(계약번호, 서비스, 차수), 단계, 한 일, 의견과 사유, 지금 상태입니다. 슈퍼관리자와 관리자는 모든 사람의 기록을 처리한 사람 칸과 함께 봅니다. 승인 취소는 이 화면이 아니라 결재 문서에서 합니다. |
| REQ-REV-07 | 가정 | **전체 진행 현황(SCR-20):** 아직 끝나지 않은 모든 계약(검토 중, 반려, 체결 대기, 운영 검토)을 오래된 기안부터 보여 줍니다. 칸은 고객사(계약번호), 서비스, 상태, 현재 진행, 영업 대표, 기안일입니다. 모두가 볼 수 있고, 열람 제한 계약은 볼 수 없는 사람에게 "열람 제한 계약"으로만 보이며 검색으로도 찾을 수 없습니다(REQ-AUTH-09). 개요의 단계 표시기에서 "계약 검토", "운영 검토"를 누르면 그 상태로 거른 채 열립니다. |
| REQ-REV-08 | 미정 | **대리 결재:** 담당자가 자리에 없을 때 다른 사람이 대신 결재할 수 있게 할지. 프로토타입에서는 슈퍼관리자가 시연용으로 담당자 대신 처리해 볼 수 있고, 결재 기록에 "누구 대신"으로 남습니다. |
| REQ-REV-09 | 가정 | **첨부 파일:** 결재 문서의 첨부 파일은 미리보기와 내려받기를 둡니다. 내려받으면 누가 언제 받았는지 기록에 남깁니다(REQ-AUTH-15). 프로토타입은 안내만 나옵니다. |
| REQ-REV-10 | 가정 | **목록 쪽 나누기와 인쇄:** 검토 대기, 검토 완료, 전체 진행 현황은 한 쪽에 20건씩 쪽 번호로 넘깁니다(REQ-ADM-04와 같은 기준). 결재 문서를 A4로 인쇄하면 처리 막대는 빠지고 결재란부터 결재 기록까지 그대로 나옵니다(REQ-FLOW-12). |

> **개발팀 참고 (REQ-REV)**
> - 결재 단계의 지금 상태는 결재 기록을 시간 순서대로 다시 적용해 만들 수 있습니다(데이터 정의서 5장 계산 규칙). 프로토타입은 `common.js`의 `buildReview`가 이 방식으로 계산합니다.
> - 누가 처리할 수 있는지(차례인 담당자, 승인 취소 조건)는 반드시 서버에서 검사해야 합니다. 화면에서 버튼을 감추는 것만으로는 막을 수 없습니다.
> - 프로토타입의 승인, 반려, 승인 취소는 브라우저에만 저장됩니다. 시연 띠의 "시연 기록 지우기"로 처음 예시 상태로 돌아갑니다.

2단계 화면 묶음(계약 체결과 운영 검토)을 만들며 정한 동작입니다(v0.23). 기획자가 정한 것은 확정, 기본안은 가정입니다.

| ID | 상태 | 요구사항 |

> **개발팀 참고 (REQ-SIGN)**
> - ⑥~⑩도 ②~⑤와 같은 결재 기록(`approval_history`)에 한 줄씩 남기고, 지금 상태는 기록을 시간 순서대로 다시 적용해 만들 수 있습니다(데이터 정의서 5장). 한 일 코드에 체결본 등록(`REGISTER`)과 다시 등록 요청(`RETURN`)이 더해졌습니다.
> - 프로토타입은 `common.js`의 `buildReview`가 ②~⑩을 함께 계산하고, `review.js`가 단계별 처리 막대와 확인 창을 그립니다. 체결본은 파일 이름만 기록하고 실제로 올리지 않습니다.
> - 확인 항목(⑥, ⑧, ⑨)을 모두 확인했는지는 서버에서도 검사해야 합니다.

### 3.8 계약 변경 절차 (REQ-CHG)

체결된 계약의 내용이 바뀌어 계약서가 새로 갱신되고 운영에 반영해야 할 때의 절차입니다. 변경 건은 원계약에 연결된 차수로 남습니다(3.3 방식 C). (panda p.38~46)

```
 ① 변경 체크리스트 작성 (영업)
 ② 체크리스트 검토 (세일즈어드민)
 ③ 영업 검토 (영업 리더, 리더 본인 건은 영업 담당 임원) ── 조건에 따라
 ④ 운영 변경 (CEM): 확정된 변경 사항을 서비스에 반영
 ⑤ 변경 완료: 원계약의 계약완료 기록 아래에 변경 사항 표시
```

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-CHG-01 | 가정 | 계약 변경으로 계약서가 새로 바뀌고 이를 운영에 반영해야 할 때, 시스템에 기록을 남깁니다. (panda p.40) |
| REQ-CHG-02 | 가정 | 계약 변경도 체크리스트 작성 → 체크리스트 검토를 거쳐 승인 여부를 정합니다. (panda p.40) |
| REQ-CHG-03 | 가정 | 변경 체크리스트: 무상 변경이면 영업 검토 없이 진행하고, 1개월 이상 기간이 바뀌는 변경이면 영업 승인이 필요합니다. (panda p.43) **[미정]** 그 밖의 기준 |
| REQ-CHG-04 | 가정 | 변경이 승인되면 CEM 담당자의 문서함에 해당 계약 건이 게시판 형태로 나타나고, CEM이 서비스에 반영한 뒤 "운영 적용 완료"로 표시합니다. (panda p.44, p.46) |
| REQ-CHG-05 | 미정 | 사용자가 바꿀 수 없는 항목은 무엇인지, 변경 이력을 어떻게 관리할지 (panda p.41). 3.3 방식 C(묶음 번호와 차수)가 이력 관리 방법이 될 수 있습니다. |
