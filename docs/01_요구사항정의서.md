## 이 문서 읽는 법

각 요구사항 앞의 표시는 결정 상태를 뜻합니다.

- **[확정]** 기획자가 직접 결정한 사항
- **[가정]** 아직 정하지 않아 업계 일반 관행으로 임시로 정한 기본안. 기획자 검토 후 바뀔 수 있음
- **[제안]** 컴플라이언스, 운영 관점에서 추가를 권하는 사항. 기획자 승인 전까지는 범위 밖
- **[미정]** 결정이 필요한 사항

요구사항 ID는 `REQ-영역-번호` 형식입니다. 프로토타입 HTML 코드의 주석에도 같은 ID를 적어, 화면, 기능이 어떤 요구사항에서 나왔는지 추적할 수 있게 합니다.

## 1. 프로젝트 개요

### 1.1 배경

현재 계약 관련 정보가 세 곳에 흩어져 있습니다.

- 내부 CRM: 계약 이력만 기록
- 내부 전자문서결재 플랫폼: 결재 문서
- 계약서 파일: 별도 보관

CLIMB은 계약 등록부터 내부 검토와 결재, 체결본 보관, 사후관리, 갱신과 만료까지를 한 곳에서 관리하는 것을 목표로 합니다.

### 1.2 시스템 명칭 (REQ-NAME)

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-NAME-01 | 확정 | 시스템 이름은 **CLIMB(클라임)**입니다. |
| REQ-NAME-02 | 확정 | 브라우저 탭 제목은 `CLIMB`으로 표시합니다. (화면별 구분이 필요하면 `대시보드 \| CLIMB`처럼 화면명을 앞에 붙임 [가정]) |
| REQ-NAME-03 | 확정 | 시스템 내부 화면에서는 한글 명칭 **무하유 계약 관리 플랫폼**을 대표 이름으로 씁니다. 로고 그림은 쓰지 않고 글자로만 표시합니다. |
| REQ-NAME-04 | 확정 | 대표 이름 아랫줄에 영문 명칭 **MUHAYU Contract Lifecycle Management ○ (CLIMB)**를 표기합니다. 헤더(화면 맨 위), 푸터(화면 맨 아래), 로그인 화면 모두 같은 두 줄 형식입니다. CLIMB은 **C**ontract **LI**fecycle **M**anagement **○**의 머리글자입니다. |
| REQ-NAME-05 | 미정 | 영문 명칭 마지막 글자 B의 의미. 후보: Base(추천), Board, Bridge, Binder. 결정 전까지 프로토타입은 **Base**로 표기 [가정] |

### 1.3 진행 방식

- **[확정]** KRDS(범정부 디자인 시스템) 구조를 따르는 HTML 화면 시안(프로토타입)을 만들면서 요구사항을 확정합니다.
- **[확정]** 실제 시스템은 사내 개발팀이 구현합니다.
- **[미정]** 사내 개발팀의 표준 기술 스택. 확인 전까지 프로토타입은 특정 프레임워크 없이 순수 HTML, CSS, JavaScript로 작성하여, 어떤 기술로든 옮기기 쉽게 합니다.

### 1.4 프로토타입의 범위

프로토타입은 **화면과 업무 흐름을 보여주는 용도**입니다. 아래 기능은 흉내만 내며 실제로 동작하지 않습니다.

| 기능 | 프로토타입 | 실제 시스템(개발팀 구현) |
|---|---|---|
| 로그인 | "Google 계정으로 로그인" 버튼만 있고, 시연용으로 역할을 골라 들어감 | Google Workspace 계정 인증 |
| 역할 전환 | 화면 맨 위 검은 띠의 "시연용 역할 전환"으로 역할별 화면을 확인 | 없음 (관리자가 지정한 역할로 고정) |
| 계약 데이터 | 화면에 미리 넣어 둔 예시 데이터 | 데이터베이스(DB) 저장 |
| 파일 업로드 | 파일 선택 화면만 있고 저장되지 않음 | 파일 저장소에 보관 |
| 알림 | 화면상 표시만 | 메일 등 실제 발송 |

**색 사용 기준 (REQ-UI-05) [가정]**

- 무하유 Green 바탕 위에 흰 글자를 쓰면 대비가 2.4:1로 기준에 못 미칩니다. 그래서 **초록 버튼의 글자는 Black**(대비 7.6:1)으로 합니다.
- 초록 계열 글자가 필요하면 Dark Green을 씁니다.
- 보조 설명 글자는 Black을 72% 농도로 쓴 회색(`#49595F`, 대비 7.3:1)을 씁니다. Gray(`#8F8F9B`)는 글자에 쓰지 않습니다.
- Pink를 바탕으로 칠한 곳(반려 배지, D-30 배지, 결재 지연 표시, 알림 숫자)은 진한 핑크(`#DC237F`) 바탕 + 흰 글자로 합니다. (REQ-UI-09)
- 반려 건 표 줄처럼 아주 연한 분홍을 깐 곳은 흰 글자가 보이지 않으므로 Black 글자를 그대로 씁니다.
- 나머지 상태 배지는 "연한 바탕 + 브랜드 색 테두리 + Black 글자"로 통일합니다.

| 계약 상태 | 색 |
|---|---|
| 작성 중 (임시 저장) | Gray |
| 검토 중 | Blue |
| 반려 | Pink |
| 체결 대기 | Purple |
| 체결 완료 | Green |
| 만료, 해지, 열람 제한 | Gray |

| 한 줄에 여러 정보를 나열 | 글자 대신 **얇은 세로선**으로 구분합니다. 줄이 바뀌면 줄 맨 앞의 세로선은 보이지 않습니다. | 한빛대학교 · 4,800만 원 · CT-2026-0412 → 한빛대학교 ｜ 4,800만 원 ｜ CT-2026-0412 |

| 문장 속 나열 | **쉼표(,)**나 "와/과"를 씁니다. | 요청자·결재자·관리자만 → 요청자, 결재자, 관리자만 |

## 3. 업무 범위와 계약 처리 흐름 (REQ-FLOW)

### 3.1 범위

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-FLOW-01 | 확정 | 관리 대상은 자사 SaaS 서비스 관련 계약입니다. 영업 기회(파이프라인) 관리는 기존 CRM에서 계속하며 CLIMB 범위에 포함하지 않습니다. |
| REQ-FLOW-02 | 확정 | 시스템 도입 이후 새로 발생하는 계약만 관리합니다. 기존 계약은 옮기지 않습니다. |

### 3.2 업무 흐름 4단계

```
 [1단계] 계약 등록 (영업)
    계약 내용 작성 → 임시 저장 → 기안
    ※ 계약서 초안 첨부, 열람 제한 여부 체크
      │
      ▼
 [2단계] 계약 검토 (부서장, 컴플라이언스, 개인정보 담당, 재무 등) ◀──┐
    본격적인 내부 검토와 결재                                         │
      ├─ 반려 → 영업 담당자가 보완 후 재기안 ─────────────────────────┘
      │
      ▼ 승인
 [3단계] 계약 체결 (영업)
    승인된 내용으로 상대방의 오프라인 서명을 받음 (시스템 밖)
    → 서명이 끝난 체결본을 시스템에 등록
      │
      ▼
 [4단계] 보관함 (모두)
    반려, 승인, 체결된 모든 계약을 보관
    변경이나 사후관리 사항은 해당 계약에 추가
      └─ 계약 조건이 바뀌는 변경, 갱신은 1단계로 돌아가 새로 기안 (원계약에 연결)
```

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-FLOW-13 | 확정 | 업무 흐름은 **계약 등록 → 계약 검토 → 계약 체결 → 보관함** 4단계입니다. 메인 메뉴는 이 흐름을 개요, 계약 등록, 계약 현황(검토와 체결 진행), 보관함으로 묶어 보여줍니다(REQ-UI-14). |
| REQ-FLOW-14 | 확정 | **계약 등록**은 계약 내용 작성과 기안입니다. [가정] 작성 중에는 임시 저장할 수 있고, 임시 저장한 계약은 작성자 본인만 봅니다. 계약번호는 기안할 때 부여합니다. |
| REQ-FLOW-03 | 확정 | **계약 검토**는 본격적인 내부 검토 단계입니다. 결재자들이 승인 또는 반려하고, 반려되면 영업 담당자가 보완해서 다시 기안할 수 있습니다(환류 구조). 내부 결재가 이 시스템의 핵심 기능입니다. |
| REQ-FLOW-04 | 확정 | **계약 체결**은 시스템 밖에서 진행합니다. 검토가 승인되면 영업 담당자가 승인된 내용을 바탕으로 각자 상대방의 오프라인 서명을 받습니다. 시스템에는 서명 기능을 두지 않습니다. |
| REQ-FLOW-05 | 확정 | 서명이 끝나면 영업 담당자가 체결본을 등록합니다. [가정] "계약 현황 > 체결 대기"에서 승인되었지만 체결본이 아직 등록되지 않은 계약을 모아 보여줍니다. |
| REQ-FLOW-15 | 확정 | **보관함**에는 반려된 계약과 승인된 계약을 포함해 그간의 모든 계약을 보관합니다. [가정] 작성 중(임시 저장) 계약은 보관함에 나오지 않습니다. |
| REQ-FLOW-16 | 확정 | 보관된 계약에서 변경이나 사후관리 요소가 생기면 해당 계약에 추가합니다. 추가하는 방식은 3.3의 제안을 따릅니다. |
| REQ-FLOW-06 | 가정 | 별도의 "이행 관리" 메뉴는 두지 않고, 보관함의 계약 상세에서 사후관리로 다룹니다. **[미정]** 사후관리 항목(대금 청구, 수금, SLA, 의무사항 등) |
| REQ-FLOW-07 | 확정 | 계약의 갱신, 만료, 해지를 관리합니다. [가정] 보관함 아래 "만료 예정 계약"에서 모아 봅니다. |
| REQ-FLOW-08 | 확정 | 갱신계약과 변경(수정)계약도 관리합니다. |
| REQ-FLOW-09 | 가정 | 갱신, 변경 계약은 원계약에 연결해 등록하고, 1단계 계약 등록부터 같은 절차를 거칩니다. 자세한 원칙은 3.3 참조 |
| REQ-FLOW-10 | 제안 | 체결본을 등록할 때 검토에서 승인된 최종본과 같은 내용인지 확인하는 단계를 둡니다(예: 등록자 확인 체크 + 컴플라이언스 확인). 승인 이후 계약서가 바뀌어 체결되는 위험을 막기 위한 통제입니다. |
| REQ-FLOW-11 | 확정 | 계약 관련 결재는 CLIMB이 기존 전자문서결재 플랫폼을 **완전히 대체**합니다. 계약 건을 기존 플랫폼에 이중으로 상신하지 않습니다. |
| REQ-FLOW-12 | 제안 | REQ-FLOW-11에 따라 CLIMB의 결재 기록이 회사의 공식 결재 증빙이 됩니다. 따라서 결재 기록(결재자, 일시, 의견, 결재 당시 첨부 문서)은 수정, 삭제할 수 없게 하고, 결재 문서를 A4로 출력할 수 있게 합니다. |
| REQ-FLOW-17 | 제안 | 반려 후 재기안은 새 계약이 아니라 **같은 계약의 다음 차수**(1차 기안, 2차 기안)로 이어 붙입니다. 이전 기안 내용과 결재 의견은 그대로 남겨 보관함에서 볼 수 있게 합니다. |

### 3.3 여러 해 이어지는 계약의 관리 원칙 [제안]

수년간 이어지는 계약을 한 건으로 볼지, 별건으로 볼지에 대한 내부통제 관점의 제안입니다. (기획자 확인 필요: C-07)

| 방식 | 내용 | 내부통제 관점 |
|---|---|---|
| A. 한 건에 덮어쓰기 | 갱신, 변경 때 기존 계약 정보를 고쳐 씀 | 추천하지 않음. 이전 조건과 승인 근거가 사라져 감사 추적이 끊김 |
| B. 모두 별건 | 갱신, 변경마다 완전히 새 계약으로 등록하고 서로 연결하지 않음 | 승인 기록은 남지만, 한 거래처와 이어지는 계약 이력을 한눈에 보기 어려움 |
| **C. 묶음 + 차수별 별건 결재 (추천)** | 원계약을 기준으로 묶고, 갱신과 변경은 각각 별건으로 기안, 결재, 체결본 등록 | 건마다 승인 근거가 남고, 묶음으로 전체 이력도 추적할 수 있음 |

방식 C를 택할 경우의 세부 원칙:

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-FLOW-18 | 제안 | **묶음 번호:** 원계약 번호를 묶음 번호로 쓰고 차수를 붙입니다. 변경은 `-A01, -A02`, 갱신은 `-R01, -R02` 예: `CT-2026-0105` → `CT-2026-0105-A01`(1차 변경), `CT-2026-0105-R01`(1차 갱신) |
| REQ-FLOW-19 | 제안 | **별건 기준:** 금액, 기간, 범위, 주요 조건처럼 권리와 의무가 바뀌면 반드시 별건으로 기안하고 결재를 받습니다. 담당자나 연락처 변경, 이행 중 특이사항 같은 사후관리 기록은 결재 없이 해당 계약에 기록으로 추가합니다(추가한 기록은 수정, 삭제 불가). |
| REQ-FLOW-20 | 제안 | **자동갱신 계약:** 만료 90일 전에 "갱신 검토"를 기안해 간단한 결재(부서장, 컴플라이언스)를 받습니다. 검토 없이 저절로 연장되는 것을 막기 위한 통제입니다. |
| REQ-FLOW-21 | 제안 | **결재 금액 기준:** 결재선을 정하는 금액은 1년 금액이 아니라 계약 전체 기간의 총액으로 합니다. 같은 거래처와 짧은 기간에 나눠 맺는 계약은 합산해 검토합니다(계약을 쪼개서 높은 결재 단계를 피하는 것 방지). |
| REQ-FLOW-22 | 제안 | **체결본 보존:** 등록된 체결본은 수정, 삭제할 수 없고, 바뀐 내용은 새 차수의 문서로만 추가합니다. |
