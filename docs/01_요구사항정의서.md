## 이 문서 읽는 법

각 요구사항 앞의 표시는 결정 상태를 뜻합니다.

- **[확정]** 기획자가 직접 결정한 사항
- **[가정]** 아직 정하지 않아 업계 일반 관행으로 임시로 정한 기본안. 기획자 검토 후 바뀔 수 있음
- **[제안]** 컴플라이언스, 운영 관점에서 추가를 권하는 사항. 기획자 승인 전까지는 범위 밖
- **[미정]** 결정이 필요한 사항
- **[제외]** 검토했지만 넣지 않기로 한 사항 (기록을 남기려고 지우지 않음)

요구사항 ID는 `REQ-영역-번호` 형식입니다. 프로토타입 HTML 코드의 주석에도 같은 ID를 적어, 화면, 기능이 어떤 요구사항에서 나왔는지 추적할 수 있게 합니다.

panda 초안에서 가져온 요구사항에는 **(panda p.쪽)**으로 출처를 적었습니다. 초안 내용은 지금 다시 확정한 것이 아니므로 대부분 [가정]으로 두었습니다.

## 1. 프로젝트 개요

### 1.1 배경

현재 계약 관련 정보가 세 곳에 흩어져 있습니다.

- 내부 CRM: 계약 이력만 기록
- 내부 전자문서결재 플랫폼: 결재 문서
- 계약서 파일: 별도 보관

CLIMB은 계약 등록부터 내부 검토와 결재, 체결본 보관, 사후관리, 갱신과 만료까지를 한 곳에서 관리하는 것을 목표로 합니다.

**목표 (panda p.3)**

- 영업 활동 단계를 세부적으로 나눠 **계약 관리, 인감 관리, 운영 관리**로 분리합니다.
- 내부통제 요소를 단계마다 녹여, 최소한의 **내부회계관리제도** 준수를 이끌어 냅니다.
- 영업자가 시스템에 계약을 쓰는 일이 별도의 행정 업무가 아니라, 계약 내용을 다시 확인하는 과정이 되도록 합니다. (panda p.16)

### 1.3 진행 방식

- **[확정]** KRDS(범정부 디자인 시스템) 구조를 따르는 HTML 화면 시안(프로토타입)을 만들면서 요구사항을 확정합니다.
- **[확정]** 실제 시스템은 사내 개발팀이 구현합니다.
- **[미정]** 사내 개발팀의 표준 기술 스택. 확인 전까지 프로토타입은 특정 프레임워크 없이 순수 HTML, CSS, JavaScript로 작성하여, 어떤 기술로든 옮기기 쉽게 합니다.

### 1.4 프로토타입의 범위

프로토타입은 **화면과 업무 흐름을 보여주는 용도**입니다. 아래 기능은 흉내만 내며 실제로 동작하지 않습니다.

| 기능 | 프로토타입 | 실제 시스템(개발팀 구현) |
|---|---|---|
| 로그인 | "Google 계정으로 로그인" 버튼만 있고, 시연용으로 역할을 골라 들어감 | Google Workspace 계정 인증 |
| 역할 전환 | 화면 맨 위 검은 띠의 "시연용 역할 전환"으로 역할별 화면을 확인 | 없음 (관리자가 지정한 역할로 고정) |
| 계약 데이터 | 화면에 미리 넣어 둔 예시 데이터 | 데이터베이스(DB) 저장 |
| 파일 업로드 | 파일 선택 화면만 있고 저장되지 않음 | 파일 저장소에 보관 |
| 알림 | 없음 (화면 알림을 두지 않음) | 이메일 발송 (REQ-ENV-09) |

### 1.5 CPQ와 CLM 범위 (REQ-SCOPE)

CLIMB은 계약 관리(CLM) 시스템이라고 부르지만, 실제로는 견적과 가격 통제(CPQ) 기능도 함께 가집니다.

| 구분 | 뜻 | CLIMB에서 다루는 것 |
|---|---|---|
| **CPQ** (Configure, Price, Quote) | 제품 구성, 가격 책정, 견적 | 제품별 구성과 금액, 서비스 기간, 표준단가표 적용 여부, 할인율 캡(할인 한도) 준수 여부, 최종 견적서 |
| **CLM** (Contract Lifecycle Management) | 계약 생애주기 관리 | 계약서 작성, 검토와 결재, 인장 날인과 체결, 보관, 운영 적용, 변경과 갱신, 종결 |

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-SCOPE-01 | 확정 | CLIMB은 **CPQ와 CLM 기능을 함께** 가집니다. 요구사항과 화면은 두 기능을 모두 고려해 만듭니다. |
| REQ-SCOPE-02 | 확정 | 가격 기준인 **표준단가표와 할인율 캡을 시스템에 저장**하되, 정해진 사람만 볼 수 있게 열람을 제한합니다. (C-13 해결. panda 초안은 영업만 알게 하는 방식이었음) [가정] 볼 수 있는 사람은 영업, 세일즈어드민, 관리자이고, 가격 기준은 관리자가 관리합니다. 계약 등록 때 제품별 금액을 넣으면 할인율과 캡 준수 여부가 자동으로 계산되어 체크리스트 2, 3번이 채워지고, 영업은 비고만 적습니다. |
| REQ-SCOPE-03 | 확정 | 영업 접수, 영업 기회, 영업 활동 관리는 지금처럼 기존 CRM에서 합니다. (REQ-FLOW-01, panda p.4, p.6) [가정] 계약을 등록할 때 CRM의 영업 기회 번호를 연결해 둡니다. |
| REQ-SCOPE-04 | 미정 | 영업 기회 단계에서 고객사에 주는 견적서를 어떻게 다룰지: 견적서에 찍는 인장 관리, 견적서에만 외부 전자서명 서비스를 쓸지 (panda p.12) |

**색 사용 기준 (REQ-UI-05) [가정]**

- 무하유 Green 바탕 위에 흰 글자를 쓰면 대비가 2.4:1로 기준에 못 미칩니다. 그래서 **초록 버튼의 글자는 Black**(대비 7.6:1)으로 합니다.
- 초록 계열 글자가 필요하면 Dark Green을 씁니다.
- 보조 설명 글자는 Black을 72% 농도로 쓴 회색(`#49595F`, 대비 7.3:1)을 씁니다. Gray(`#8F8F9B`)는 글자에 쓰지 않습니다.

- 나머지 상태 배지는 "연한 바탕 + 브랜드 색 테두리 + Black 글자"로 통일합니다.

### 3.2 업무 흐름 5단계와 세부 단계

CLIMB의 업무 흐름은 5단계이고, 각 단계 안에서 panda 초안의 세부 단계(①~⑪)를 거칩니다. (panda p.4, p.34~37) v0.13에서 4단계 "보관함"을 **운영 검토**와 **계약 완료**로 나눴습니다.

```
 [1단계] 계약 등록 (영업)
    ① 계약품의 작성: 계약 내용 + 체크리스트(표준계약서, 표준단가표, 할인율 캡) → 기안
       ※ 임시 저장, 계약서 초안 첨부, 열람 제한 여부 체크
      │
      ▼
 [2단계] 계약 검토 ◀────────── 반려되면 기안자(영업)에게 돌아가 보완 후 재기안
    ② 체크리스트 검토 (세일즈어드민) ──── 항상
    ③ 법무 검토 (법무) ──────────────── 표준계약서를 쓰지 않을 때
    ④ 개인정보 검토 (개인정보 담당) ───── 개인정보를 처리할 때 [CLIMB 추가]
    ⑤ 영업 검토 (영업 리더, 리더 본인 건은 영업 담당 임원) ── 가격 조건이 기준을 벗어날 때
      │
      ▼ 승인
 [3단계] 계약 체결
```

### 3.3 여러 해 이어지는 계약의 관리 원칙

수년간 이어지는 계약을 한 건으로 볼지, 별건으로 볼지에 대한 원칙입니다. **방식 C와 세부 원칙을 모두 채택했습니다.** (C-07 해결)

| 방식 | 내용 | 내부통제 관점 |
|---|---|---|
| A. 한 건에 덮어쓰기 | 갱신, 변경 때 기존 계약 정보를 고쳐 씀 | 추천하지 않음. 이전 조건과 승인 근거가 사라져 감사 추적이 끊김 |
| B. 모두 별건 | 갱신, 변경마다 완전히 새 계약으로 등록하고 서로 연결하지 않음 | 승인 기록은 남지만, 한 거래처와 이어지는 계약 이력을 한눈에 보기 어려움 |
| **C. 묶음 + 차수별 별건 결재 (추천)** | 원계약을 기준으로 묶고, 갱신과 변경은 각각 별건으로 기안, 결재, 체결본 등록 | 건마다 승인 근거가 남고, 묶음으로 전체 이력도 추적할 수 있음 |

방식 C의 세부 원칙:

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-FLOW-18 | 확정 | **묶음 번호:** 원계약 번호를 묶음 번호로 쓰고 차수를 붙입니다. 변경은 `-A01, -A02`, 갱신은 `-R01, -R02` 예: `CT-2026-0105` → `CT-2026-0105-A01`(1차 변경), `CT-2026-0105-R01`(1차 갱신) |

> **개발팀 참고 (REQ-REG-06, 07, 09)**
> - 체크리스트 2, 3번 계산과 결재선 결정은 화면에서 미리 보여 주는 것이고, 화면 값은 사용자가 바꿀 수 있으므로 **서버에서 가격 기준으로 다시 계산해 검증**해야 합니다.
> - 할인율 = (표준 단가 x 수량 - 계약 금액) / (표준 단가 x 수량). 2번은 할인한 제품이 하나라도 있으면 "아니오", 3번은 할인율이 그 제품의 캡을 넘는 제품이 하나라도 있으면 "아니오"입니다.
> - 프로토타입의 가격 기준 값(`mock-data.js`의 `PRICE_BOOK`: 제품 코드, 표준 단가, 할인율 캡)은 화면 시연용 **가상 값**입니다. 실제 값은 관리자가 "가격 기준 관리"(SCR-54)에서 넣습니다.
> - 계약번호 일련번호는 서버에서 기안 순서대로 부여해야 하며, 화면의 번호는 예시입니다.

### 3.8 계약 변경 절차 (REQ-CHG)

체결된 계약의 내용이 바뀌어 계약서가 새로 갱신되고 운영에 반영해야 할 때의 절차입니다. 변경 건은 원계약에 연결된 차수로 남습니다(3.3 방식 C). (panda p.38~46)

```
 ① 변경 체크리스트 작성 (영업)
 ② 체크리스트 검토 (세일즈어드민)
 ③ 영업 검토 (영업 리더, 리더 본인 건은 영업 담당 임원) ── 조건에 따라
 ④ 운영 변경 (CEM): 확정된 변경 사항을 서비스에 반영
 ⑤ 변경 완료: 원계약의 계약완료 기록 아래에 변경 사항 표시
```

| ID | 상태 | 요구사항 |
|---|---|---|
| REQ-CHG-01 | 가정 | 계약 변경으로 계약서가 새로 바뀌고 이를 운영에 반영해야 할 때, 시스템에 기록을 남깁니다. (panda p.40) |
| REQ-CHG-02 | 가정 | 계약 변경도 체크리스트 작성 → 체크리스트 검토를 거쳐 승인 여부를 정합니다. (panda p.40) |
| REQ-CHG-03 | 가정 | 변경 체크리스트: 무상 변경이면 영업 검토 없이 진행하고, 1개월 이상 기간이 바뀌는 변경이면 영업 승인이 필요합니다. (panda p.43) **[미정]** 그 밖의 기준 |

## 8. 추후 결정 항목

기획자가 차차 결정할 항목입니다. 결정 전까지 프로토타입은 [가정]으로 표시한 기본안으로 만듭니다.

| 영역 | 결정할 내용 |
|---|---|
| 시스템 연동 | CRM(고객, 딜 정보 불러오기), 전자서명 서비스, 메일, 메신저 알림 연동 여부 |
| 계약 유형 | 관리할 계약 유형 목록과 유형별 입력 항목, 절차 차이 |
| 계약 정보 | 계약 한 건에 기록할 필수 항목 (기존 계약관리대장 양식이 있으면 활용) |
| 계약 상태 | 상태값 목록과 상태가 바뀌는 규칙 |
| 파일 | 초안, 수정본 버전 관리, 체결본, 부속서류 보관 방식 |
| 거래처 | 거래처 목록 별도 관리 여부, 상대방 확인 항목(제재, 반부패 등) |
| 사후관리 | 보관함에서 관리할 사후관리 항목(청구, 수금, SLA, 의무사항 등) |
| 감사 기록 | 열람, 수정, 승인, 다운로드 중 기록 범위와 보관 기간 |
| 계약 게시물과 출력 | 계약 한 건을 게시물 형태로 DB에 보관하고, 그 게시물을 A4로 출력할 수 있는 형태로 정리하는 방식 (기획자가 추후 결정, REQ-DOC-01~02, REQ-FLOW-12 참고) |
| 보존, 파기 | 계약 종료 후 보존 연한과 파기 절차 |
| 개인정보 | 계약서 내 개인정보 마스킹, 다운로드 제한 |

| 알림 | 이메일 알림을 보내는 시점(만료 D-90/60/30, 해지통지 기한, 결재 차례, 반려 등)과 받는 사람. 수단은 이메일로 확정(REQ-ENV-09) |
| 재무 관련 항목 | 계약 등록의 수불부 연동, 세금계산서, 매입 항목의 입력 형식 (3.4) |

| 운영 적용 대상 | CK, HR 외에 운영 적용이 필요한 서비스와 설정 항목 (REQ-FLOW-25) |
