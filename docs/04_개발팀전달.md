## 1. 이 문서를 읽는 법

기획자는 CLIMB의 **무엇을 만들지**를 화면 시안과 문서로 정했습니다. **어떻게 만들지**(화면 기술, 서버, 데이터베이스, 운영 환경)는 개발팀이 정합니다. 기획자는 특정 기술을 권하지 않습니다.

이 문서는 세 가지를 적습니다.

1. 전달하는 것: 기획자가 만들어 둔 문서와 화면 시안 (2장)
2. 시안에 없는 것: 실제 시스템에서 새로 만들어야 하는 것 (3장)
3. 정할 것: 개발팀이 정할 것(4장)과 기획자가 아직 정하지 않은 것(5장)

### 2.2 화면 시안(`prototype/`)

- **만든 기술:** HTML, CSS, JavaScript만 썼고 외부 라이브러리는 없습니다(글꼴만 Google Fonts의 Noto Sans KR). 설치나 빌드 없이 열립니다. 이렇게 만든 이유는 요구사항 정의서 1.4에 있습니다.
- **화면:** 로그인과 이용 안내를 포함한 화면 24개(메뉴에 있는 모든 화면). 화면 크기는 A4 세로 종이 폭이고 인쇄하면 A4 문서로 나옵니다. 휴대폰 크기(600px 이하)도 맞춰 두었습니다.
- **여는 법:** `Projects/CLM`에서 `python serve.py`를 실행하고 http://localhost:8730 을 엽니다. 화면 맨 위 검은 띠의 "시연용 역할 전환"으로 역할을 바꿔 가며 볼 수 있습니다.

## 3. 시안에 없는 것(실제 시스템에서 새로 만들 것)

시안은 브라우저 안에서만 동작합니다. 아래는 모두 실제 시스템에서 새로 만들어야 합니다.

| 영역 | 해야 할 일 | 관련 요구사항 |
|---|---|---|
| 로그인 | 회사 Google 계정 로그인(회사 도메인만), 2단계 인증, 30분 동안 아무것도 하지 않으면 자동 로그아웃 | REQ-ENV-03, REQ-SEC-02, 03 |
| 권한 | 역할(분야와 등급)에 따른 화면, 기능, 파일 접근을 **서버에서** 확인. 열람 제한 계약, 대리 지정, 관리자 기능 포함. (v0.7) 열람 제한 계약의 지정 열람자(조직은 지금 그 조직 사람, 사람은 풀리지 않은 지정만)도 서버에서 판단하고, 사용자 조직이 바뀌는 순간(사용자 권한 관리, 조직 옮기기. 인사 시스템과 이으면 그 발령) 사람 지정을 풀고 관리자에게 이메일 | 4장, REQ-AUTH, REQ-SEC-05 |
| 데이터 저장 | 계약(기관 또는 부서명은 계약마다 직접 적음), 결재 기록, 거래처, 사용자, 코드, 제품과 기능(서비스는 제품에 저절로 붙음), 가격 기준(기능마다 하나), 변경 이력. 기록은 고치거나 지우지 않고 남김. 계약의 제품 줄에는 기안 당시 제품, 기능, 플랜 이름을 함께 남김 | 데이터 정의서 4장, 8장, 8-5장 |
| 첨부 파일 | 계약서 초안, 조항 대비표, 체결본 저장(형식과 크기 제한, 영구 보존, 암호화) | REQ-REG-15, REQ-FLOW-30, REQ-SEC-11 |
| 워터마크와 내려받기 | 인쇄, PDF 저장, 내려받은 PDF에 출력자 워터마크. 원본은 기안자, 법무, 관리자만. 내려받기 기록 | REQ-SEC-07, 08 |
| 이메일 알림 | 결재 차례, 반려, 보완 요청, 회계 영향 조건, 만료 60일 전과 30일 전, 중요 공지(전체 사용자), 열람자 지정(지정된 사람, 조직이면 그 조직 사람 모두)과 지정 풀림(관리자, v0.7) 등. 사용자마다 선택 알림을 켜고 끄는 설정(내 계정 SCR-93)을 지킴 | REQ-UI-29, 30, REQ-ENV-09, REQ-CHK-08 |
| 접속과 작업 기록 | 영구 보관, 매월 점검, 이상 행위 알림, 시간 초과 로그아웃 표시 | REQ-AUTH-13, REQ-SEC-06, REQ-ADM-02, 18~22 |
| 외부 조회 | 직접 넣은 사업자등록번호의 국세청 상태 조회(폐업 막음, 휴업 알림. 상호는 가져오지 않음) | REQ-REG-18 |
| 사업자 정보 DB | 기획자가 모은 거래처 자료(추후 전달)를 넣고, 기준일 표시 | REQ-REG-19 |
| 기존 자료 옮기기 | 기존 계약관리대장의 계약과 거래처를 옮기고 새 계약번호(2610CL001 꼴)를 붙임 | REQ-REG-22 |
| 개인정보 | 계약 종료 10년 뒤 계약 안의 개인정보 분리 보관 | REQ-SEC-10 |
| 보안과 운영 | 사내망과 VPN에서만 접속, 관리자 기능은 사내망에서만, 암호화, 백업과 복구, 취약점 점검, 데이터는 국내에 둠 | REQ-ENV-02, REQ-SEC-04, 11~16 |

## 4. 개발팀이 정할 것

기획자는 아래를 정하지 않았습니다. 사내 개발팀의 기준 기술과 유지보수 여건에 맞게 정해 주세요. 요구사항 정의서 1.4의 "사내 개발팀의 표준 기술 스택"이 [미정]으로 남아 있습니다.

| 항목 | 정할 내용 | 지켜야 할 요구사항 |
|---|---|---|
| 화면 기술 | 시안(순수 HTML)을 어떤 화면 기술로 옮길지 | 화면 배치와 문구는 시안대로, A4 인쇄(REQ-UI-10, 11), 휴대폰 크기(REQ-ENV-07, 08), KRDS(REQ-UI-01), 접근성(REQ-UI-21) |
| 서버 기술과 언어 | 서버를 무엇으로 만들지 | 권한과 입력 검사는 서버에서 다시 확인 |
| 데이터베이스 | 어떤 데이터베이스를 쓰고 데이터 정의서를 어떻게 테이블로 옮길지 | 코드값 원칙(코드와 화면 이름을 나눔, 쓴 코드는 지우지 않음), 기록은 고치거나 지우지 않음 |
| 로그인 구현 | Google 계정 로그인을 어떤 방식으로 붙일지, 2단계 인증을 어떻게 강제할지 | REQ-ENV-03, REQ-SEC-02, 03 |
| 파일 저장소 | 첨부 파일을 사내 서버에 둘지 다른 저장소에 둘지, 암호화 방식 | 영구 보존, 국내 보관(REQ-SEC-16) |
| PDF와 워터마크 | 워터마크 PDF를 어디서 어떻게 만들지 | REQ-SEC-07, 08 |
| 이메일 발송 | 어떤 메일 서비스로 보낼지 | REQ-ENV-09 |
| 배포와 운영 환경 | 서버를 어디에 둘지, 개발, 시험, 운영 환경 나누기 | REQ-ENV-02, REQ-SEC-04, 13, 16 |
| 기록 저장과 점검 도구 | 접속, 작업 기록을 어디에 어떻게 영구 보관하고 점검 화면(SCR-57)에 보일지 | REQ-AUTH-13, REQ-SEC-06 |
| 글꼴 제공 | Google Fonts가 사내망에서 막히면 글꼴 파일을 서버에 둘지 | REQ-UI-02 |
| 국세청 조회 연동 | 국세청 사업자등록 상태 조회를 어떻게 붙일지(인증키 관리 포함) | REQ-REG-18 |
| 지원 브라우저 | 어떤 브라우저와 버전까지 지원할지 | REQ-ENV-04 [가정] Chrome 최신 |
| 사용 규모 | 사용자 약 40명 기준의 서버 규모와 성능 목표 | REQ-SCALE-02 |
| 시험과 보안 점검 | 오픈 전 기능 시험, 취약점 점검 방법. 화면 시험은 기획자가 정한 기준 기기로 함: PC(마우스, A4 화면), 아이폰 18 Pro(402 x 874), 아이패드 프로 11인치(세로 834 x 1210, 가로 1210 x 834). 태블릿은 PC 화면, 휴대폰 화면 규칙은 스마트폰에만(폭 600px 이하, 또는 터치 화면이면서 높이 600px 이하인 가로 스마트폰, v0.6). 가로 스마트폰은 터치 화면으로 흉내 내야 휴대폰 규칙이 적용됨 | REQ-SEC-01(ISMS-P 수준), 14, REQ-ENV-07 |

## 5. 기획자가 아직 정하지 않은 것

2026-10-21에 남은 항목을 기획자가 정리했습니다(요구사항 정의서 v0.39, 데이터 정의서 v0.22). 아래 5개만 남아 있고, 모두 다른 부서의 확인이나 자료가 필요합니다. 정해지면 문서에 바로 반영합니다. (D-10은 2026-10-22에 해결: 서비스는 한 단계, 그 아래 제품 → 기능 → 플랜, 요구사항 정의서 v0.47)

| 번호 | 내용 | 누구와 정함 | 개발에 미치는 영향 | 지금 시안 |
|---|---|---|---|---|
| C-18 | 해지와 그대로 연장에서 ⑥ 날인~⑧ 체결본 확인을 거칠지, 신규와 운영 변경에 ⑩ 재무 확인이 필요한지 | 재무 | 결재 단계 흐름 | ⑥~⑧ 거치지 않음, 운영 변경은 ⑩ 없음 |
| C-19 | 계약서 없이 견적서로 계약을 갈음하는 경로를 둘지(재무 제안: 5백만 원 미만) | 재무 | 새 등록 흐름이 생길 수 있음 | 없음 |
| D-07 | 수불부 연동, 세금계산서, 매입 칸의 입력 형식 | 재무 | 항목 형식 | 선택 칸(형식 미정 표시) |
| D-12 | 계약 종료 10년 뒤에도 분리 보관하는 개인정보를 계속 둘지 파기할지 | 법무 | 보관, 파기 처리 | 정하지 않음 |
| D-09 | 서비스, 제품, 기능과 기능마다 가격 전체 목록. 이름으로 서비스를 알 수 없는 제품(프리즘, 몬스터 등)은 서비스 짝도 함께(요구사항 정의서 C-27) | 기획자가 엑셀로 전달 | 코드, 제품과 기능, 가격 기준 데이터 | 서비스 2개(카피킬러, HR 서비스), 제품 6개, 기능 11개(프리즘의 8개는 기획자 예시, 나머지와 모든 가격은 가상) |

이 밖에 문서에서 **[가정]**으로 표시한 것은 기획자의 기본안입니다. 개발을 시작하기 전에 개발팀이 보기에 무리가 있는 가정이 있으면 기획자에게 알려 주세요.
