## 1. 이 문서를 읽는 법

기획자는 climb의 **무엇을 만들지**를 화면 시안과 문서로 정했습니다. **어떻게 만들지**(화면 기술, 서버, 데이터베이스, 운영 환경)는 개발팀이 정합니다. 기획자는 특정 기술을 권하지 않습니다.

이 문서는 세 가지를 적습니다.

1. 전달하는 것: 기획자가 만들어 둔 문서와 화면 시안, 코드 지도 (2장)
2. 시안에 없는 것: 실제 시스템에서 새로 만들어야 하는 것 (3장)
3. 정할 것: 개발팀이 정할 것(4장)과 기획자가 아직 정하지 않은 것(5장)

### 2.2 화면 시안(`prototype/`)

- **만든 기술:** HTML, CSS, JavaScript만 썼고 외부 라이브러리는 없습니다(글꼴만 Google Fonts의 Noto Sans KR과 로고 영어에 쓰는 jsDelivr의 SUITE). 설치나 빌드 없이 열립니다. 이렇게 만든 이유는 요구사항 정의서 1.3에 있습니다.
- **화면:** 로그인과 이용 안내를 포함한 화면 34개입니다. HTML 파일 수로 셌고, 메뉴에 있는 모든 화면과 메뉴 없이 들어가는 상세 화면을 넣었습니다(v0.17에 견적 quote.html, quotes.html을 더함). 요구사항 정의서는 35개 화면으로 셉니다. 새 견적과 견적서 보기(SCR-15, 17)가 한 파일이기 때문입니다(v0.21). 화면 크기는 A4 세로 종이 폭이고 인쇄하면 A4 문서로 나옵니다. 휴대폰 크기(600px 이하)도 맞춰 두었습니다.
- **여는 법:** `Projects/climb`에서 `python serve.py`를 실행하고 http://localhost:8730 을 엽니다. 화면 맨 위 검은 띠의 "시연용 역할 전환"으로 역할을 바꿔 가며 볼 수 있습니다.

### 2.4 코드 지도 (v0.10)

시안 코드는 화면마다 HTML 하나와 그 화면의 JS 하나로 나뉘고, 모든 화면이 아래 파일을 함께 씁니다. 처음 볼 때는 이 순서로 읽으면 됩니다.

| 순서 | 파일 | 하는 일 |
|---|---|---|
| 1 | `assets/css/tokens.css` | 색, 글자 크기, 간격 값. 색은 무하유 8가지만 쓰고, 어두운 화면 값도 여기 있음. 다른 CSS는 색을 직접 쓰지 않고 이 값을 씀. (v0.15) 간격은 이름 7개(`--gap-item` 등)로 모음. 인쇄용 흑백 색(6-1, `@media print`)과 대비 높이기 색(8, `prefers-contrast: more`)도 여기 |
| 2 | `assets/css/common.css` | 모든 화면의 뼈대: 헤더, 메뉴, 푸터, 버튼, 표, 배지, 안내 상자, 창, 휴대폰 화면(v0.16 오른쪽 메뉴판, v0.17 머리글 아이콘 셋과 판. v0.15의 아래 탭 막대는 없앰), 인쇄(v0.15 흑백). 맨 위에 차례. (v0.15) 맨 끝 16장은 기기의 접근성 설정(동작 줄이기, 윈도우 고대비) |
| 3 | `assets/js/theme.js` | 화면을 그리기 전에 밝은 화면, 어두운 화면을 정함(모든 HTML의 `<head>`) |
| 4 | `assets/js/mock-data.js` | 예시 데이터(`window.CLIMB_DATA`, 화면 코드에서는 `D`). 데이터 정의서와 같은 이름의 묶음과 코드표 |
| 5 | `assets/js/common.js` | 공통 기능(`window.CLIMB`, 화면 코드에서는 `C`). 맨 위에 차례, 맨 아래에 화면 코드가 쓰는 이름을 묶음별로 내보냄 |
| 6 | 화면 JS(`assets/js/화면.js`) | 그 화면만의 그리기와 동작. 파일 맨 위 주석에 화면 ID, 하는 일, 관련 요구사항 |

**common.js 안의 묶음**(위에서 아래 순서, 파일 맨 위 차례와 같음): 메뉴 구조 → 아이콘과 시스템 이름 → 시연용 역할 → 날짜와 금액 표시 → 계약과 결재 이름 → 표준계약서와 판 → 사업자등록번호 → 영업기회번호 → 결재 흐름 계산(체크리스트로 결재선, 결재 기록으로 지금 상태) → 열람 권한 → 처리 대기 목록 → 시연 기록 → 견적서 → 체결 후 의무 → 관리자 설정 → 계약 묶음(만료 예정, 해지 통지 기한) → HTML 조각 → 헤더, 메뉴, 푸터 그리기 → 메뉴 검색 → 휴대폰 전체 메뉴판 → 안내 메시지와 확인 창 → 입력 칸 → 쪽 번호 → 관리자 화면 부품 → 워터마크 → 날짜 입력과 달력 → 표 머리글 정렬 → 화면 시작(`C.init`)과 내보내기. (v0.21: 견적서, 메뉴 검색, 휴대폰 전체 메뉴판, 표 머리글 정렬을 더함. v0.60에 없앤 "맨 위로"는 목록에서 뺌)

**휴대폰의 표 칸 폭(v0.21)**: 표는 `.tbl-scroll` 안에서 옆으로 밀어 보고, 휴대폰에서만 칸 폭 아래한도를 둡니다(`common.css` 휴대폰 묶음). 글이 긴 칸(의견, 사유, 담당자 설명)은 머리글에 `.col-phone-wide`(16rem), 조직과 이름이나 판처럼 짧은 칸은 `.col-phone-mid`(10rem)나 칸에 `.cell-phone-nowrap`. 이 표시가 없으면 줄바꿈하지 않는 다른 칸에 밀려 두세 글자씩 꺾입니다. PC와 인쇄는 A4 폭 안에서 넉넉해 바꾸지 않습니다. 이용 안내 표는 `help.css`의 `.col-wide`. 표 안의 날짜는 `common.js`의 `keepDates`가 그린 뒤 날짜마다 `.keep`으로 묶어 하이픈에서 꺾이지 않게 합니다(REQ-UI-25, 표 머리글 정렬과 같은 때에 돎). 옮길 때는 날짜를 그리는 부품에서 처음부터 묶으면 됩니다. 입력 칸 설명은 `C.wireFields`가 `aria-describedby`로 잇는데, 체크 하나만 든 칸은 체크 자체에 잇습니다(화면낭독기는 div의 설명을 읽지 않음).

**옮길 때 정답지로 쓸 곳**: 결재선과 결재 상태(`C.reviewRoute`, `buildReview`), 계약 묶음(`C.bundleOf`), 열람 권한(`C.canView`), 해지 통지 기한(`C.noticeDate`), 의무 상태(`C.obligationState`), 통계 세는 법(`stats.js` 맨 위 주석과 데이터 정의서 2-1장). 같은 결과가 나오게 서버에서 다시 만들면 됩니다.

**시안 전용이라 옮기지 않을 것**: 시연용 역할 띠(`renderDemoBar`), `localStorage`의 `climb.*` 시연 기록, 화면에서만 흉내 낸 권한 확인.

### 2.5 시안 코드에 남겨 둔 겹침 (v0.10)

시안은 화면을 빨리 바꿔 보는 용도라, 아래처럼 여러 화면에 비슷한 코드가 따로 있습니다. 동작은 같게 맞춰 두었지만 시안에서 하나로 합치지는 않았습니다. 실제 시스템으로 옮길 때 공통 부품이나 서버 규칙 하나로 만들면 됩니다.

|---|---|---|
| 목록 화면의 틀(거르기 줄, 검색, 쪽 번호, 빈 목록 문구) | `contracts.js`, `progress.js`, `my-contracts.js`, `review-queue.js`, `review-done.js`, `signing.js`, `ops-queue.js`, `expiring.js`, `obligations.js`, 관리자 목록 화면 | 목록 부품 하나 |
| 창 열고 닫기(초점 옮기기, Esc로 닫기, 바깥 누르면 닫기) | `C.formModal`과 결재 문서, 계약 상세, 관리자 화면의 창 | 창 부품 하나 |

### 4.1 [제안] 데이터베이스와 ERP, CRM 내보내기 (v0.12, 기획자 참고)

기획자가 2026-10-23에 조사해 정리한 **참고안**입니다. 기술은 개발팀이 정하며(1장), 개발팀의 기준 기술이 따로 있으면 그것을 따릅니다.

**데이터베이스: PostgreSQL을 권함**

| 안 | 맞는 경우 | 주의 |
|---|---|---|
| A. PostgreSQL (권함) | 새로 만드는 시스템, 국내 클라우드 | 개발팀이 처음 쓰면 익히는 시간 |
| B. MySQL, MariaDB | 개발팀이 이미 쓰고 있을 때 | 이 규모(사용자 약 40명, REQ-SCALE-02)에서는 기능 차이가 작음 |
| C. 사내 ERP와 같은 DB(예: MS SQL) | ERP 팀이 그 DB를 이미 운영 중일 때 | 라이선스 비용이 들고, DB끼리 직접 잇고 싶어짐(아래 1번과 어긋남) |

PostgreSQL을 권하는 까닭:
- 가장 널리 쓰임: 2025년 Stack Overflow 개발자 설문에서 사용률 약 56%로 1위이고, 계속 쓰고 싶은 DB로도 1위. 사람을 구하거나 자료를 찾기 쉬움
- 라이선스 비용 없음(오픈소스)
- 국내 관리형 서비스로 쓸 수 있음: 네이버 클라우드 Cloud DB for PostgreSQL(공공기관용 CSAP 인증을 받은 DB 상품 가운데 하나), NHN Cloud RDS for PostgreSQL, AWS 서울 리전. 데이터를 국내에 두는 요구(REQ-SEC-16)와 백업, 복구(REQ-SEC-13)를 맞추기 쉬움
- 요구사항과 맞는 기능: 금액을 오차 없는 숫자(`numeric`)로 저장, 접속과 작업 기록 확장 기능(pgAudit, REQ-AUTH-13, REQ-SEC-06), 행마다 권한을 거는 기능(Row Level Security, 열람 제한 REQ-AUTH-09를 서버에서 판단할 때 도움), 설정처럼 모양이 바뀌는 값은 JSON 칸

**ERP, CRM 내보내기 설계 (DB 종류보다 이것이 더 중요)**
1. **외부 시스템이 climb DB에 직접 붙지 않음.** climb가 내보내는 창구(API나 정해진 형식의 파일)를 따로 둠. DB 구조가 바뀌어도 연동이 깨지지 않고, 열람 제한과 권한이 지켜지며, 내보낸 기록이 남음(REQ-AUTH-13)
2. **보낼 목록 표(transactional outbox).** 계약 완료, 해지, 운영 변경 완료처럼 밖에 알릴 일이 생기면 같은 저장(트랜잭션) 안에서 보낼 목록에 한 줄을 적고, 따로 도는 작업이 ERP, CRM으로 보냄. "저장은 됐는데 전송이 실패해 서로 어긋남"을 막음. 실패하면 다시 보내고, 몇 번째 보냈는지와 결과를 남김. 이 규모에서는 몇 분마다 확인하는 방식으로 충분하며 Kafka 같은 큰 도구는 필요 없음
3. **바깥 번호 짝 표.** climb 계약번호와 ERP 매출 전표 번호, climb 거래처와 ERP 거래처 코드, 판다 영업기회번호(이미 받음, REQ-REG-21)를 짝지어 둠(예: `external_ref`: 대상, climb 번호, 바깥 시스템, 바깥 번호, 맞춘 일시)
4. **코드는 영문 코드로 저장**(데이터 정의서 코드값 원칙). ERP와 CRM의 코드와 짝 맞추는 표를 둠
5. **금액은 원 단위 숫자, 날짜와 일시는 기준 시간대를 정해 저장**(화면은 한국 시간)
6. **ERP 연계 방식은 재무팀과 ERP 업체에 확인.** 참고로 더존 ERP(iU)에 연계하는 다른 서비스들은 결재 완료 데이터를 ERP의 자동전표 표에 넣거나 엑셀로 일괄 등록하는 방식을 씀. 아마란스10의 공개 연동 문서는 찾지 못함

참고한 자료: Stack Overflow 2025 설문 정리(blog.vonng.com, enterprisedb.com), 네이버 클라우드 CSAP 인증 상품 기사(venturesquare.net)와 Cloud DB for PostgreSQL 안내(guide.ncloud-docs.com), NHN Cloud RDS for PostgreSQL 안내(docs.nhncloud.com), transactional outbox 설명(conduktor.io), pgAudit 안내(oneuptime.com), 더존 iU 연계 방식(docs.bizplay.co.kr)
