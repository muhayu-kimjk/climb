## 이 문서 읽는 법

이 문서는 climb의 통제를 기준 문서에 비추어 본 대응표입니다. 이미 갖춘 통제(2장), 빈 곳(3장), 기획자가 정할 것(4장), 다음에 할 일(5장)을 한곳에 모았습니다. 이 문서는 요구사항을 바꾸지 않습니다. 기획자가 받아들인 것만 요구사항 정의서(01)와 다른 문서로 옮깁니다.

기획자는 이 시스템의 본질을 CPQ로 봅니다. 수주한 영업 기회에서 견적, 계약으로 이어지는 길을 표준화하고 투명하게 하는 것입니다(01 3.9). 그래서 빈 곳도 이 길의 단계(영업 기회, 견적, 가격, 결재, 계약, 체결, 운영 넘김, 체결 후)와 이 길을 받치는 것(기준 정보, 접근과 보안, 기록, 보고, 기타)으로 나눴습니다.

**빈 곳을 찾은 방법**

1. 검토자 넷이 나눠 정리했습니다. 셋은 기준에서 climb에 걸리는 요구를 뽑았고(내부회계 43개, ISO 37001과 37301 35개, ISO/IEC 27001과 42001 44개), 하나는 climb의 지금 기능 75개를 문서와 시안 코드에서 정리했습니다.
2. 한 명이 둘을 맞춰 보고 빈 곳 30개(G-01~G-30)와 이미 갖춘 통제 30개를 뽑았습니다.
3. 빈 곳마다 다른 검토자가 문서와 시안 코드를 따로 다시 읽어, 이미 있는 것과 기획자 결정과 어긋나는 것을 가려냈습니다. 그 결과 G-01은 뺐고(3장 처음), 나머지 29개는 이 확인에 맞춰 범위를 좁히거나 고쳐 적었습니다. 처음 제안이 기획자 결정과 어긋나면 기획자 결정을 따르고, 그 부분은 "뺍니다" 또는 "기획자 결정"으로 적었습니다.

**우선순위와 크기**

| 표시 | 뜻 |
|---|---|
| P1 | 매출 과정의 핵심 통제라 내부회계 감사에서 먼저 볼 가능성이 큰 것. 운영 시작 전에 정하기를 권합니다 |
| P2 | 부패방지, 컴플라이언스, 정보보안을 단단하게 하는 것. 운영 첫해 안에 권합니다 |
| P3 | 있으면 좋은 것 |
| S | 화면 한두 곳의 작은 변경이나 문서 몇 줄 |
| M | 화면 여러 곳과 데이터 정의서 변경 |
| L | 새 화면이나 다른 시스템과의 연결이 필요함 |

크기는 기획자가 순서를 정하도록 돕는 대략의 값이며 개발팀의 일정 추정이 아닙니다. "S~M"은 고르는 안에 따라 달라진다는 뜻입니다. 다시 확인에서 우선순위나 크기, 결정 필요 여부가 바뀐 것은 괄호에 처음 값을 적었습니다.

**표시와 인용**

- [제안]은 이 문서가 권하는 것, [가정]은 회사 사정을 확인하지 못해 임시로 둔 것입니다. 01의 표시와 뜻이 같습니다.
- ISO와 IEC 표준은 문장을 옮기지 않고 조항 번호와 우리말 요약만 적습니다. 금융감독원 자료도 원칙 번호와 뜻만 적습니다. 01 3.6.1처럼 원문과 문장 단위로 대조하지 않았으므로, 적용할 때는 재무팀이나 외부감사인의 확인을 권합니다.
- 기획자가 정할 것이 있는 빈 곳은 4장에 질문으로 다시 모았습니다.
- 빈 곳 번호는 분석 기록과 맞추려고 바꾸지 않았습니다. 그래서 G-02부터 시작합니다.

## 3. 빈 곳

**G-01은 뺐습니다.** 처음 분석은 "견적 기록이 없어 견적을 계약까지 따라갈 수 없고, 승인 전에 약속한 할인이 보이지 않음"을 빈 곳으로 보았습니다. v0.61에서 견적서를 이 시스템에서 발급하기로 하면서(01 3.9 REQ-QUO-01~08, SCR-15~17, 데이터 정의서 8-8) 누가, 언제, 어떤 판, 얼마로 견적을 냈는지 남고, 한도를 넘는 줄은 견적을 만들 때 알려 줍니다. 견적과 계약을 잇자는 처음 제안은 기획자 결정(REQ-QUO-01: 견적은 계약과 이어지지 않음)과 맞지 않습니다. 두 기록은 영업기회번호로 영업 기회 단위에서 이어집니다. 남은 작은 것은 [제안]으로만 적습니다: 견적 목록(SCR-16)에서 한도 넘은 견적 거르기, 통계(SCR-46)에 한도 넘은 견적 수 세기(v0.3 반영: 01 REQ-QUO-09, REQ-DASH-19). 견적 단계 할인의 남는 위험(01 3.6.1)은 G-27의 남는 위험 수용 기록에 올립니다.

- **지금 있는 것:** 덧붙이기만 되는 저장과 표준 시각 맞추기(01 2.1 개발 메모), 업무 데이터와 떨어진 쓰기 전용 접속 기록, 매일 백업(REQ-SEC-15)이 있습니다. 정보보호가 매월과 분기 점검을 하는 것은 기획자 결정이고, 최고관리자도 접속 기록 점검을 씁니다(REQ-ADM-18).
- **빠진 것:** 결재 기록, 관리자 변경 이력, 접속 기록이 바뀌지 않았음을 알아내는 장치가 없습니다. 결재 기록과 관리자 변경 이력은 "고치거나 지울 수 없음"만 있고, 따로 떨어진 저장은 접속 기록뿐입니다. 최고관리자가 자기 작업이 든 점검을 승인할 수 있습니다. 데이터를 직접 고치는 절차(요청, 승인, 기록)가 없습니다.
- **제안:** [제안] ① 세 기록에 앞 기록의 지문을 이어 붙이고 매일 확인해, 깨지면 정보보호에 이메일을 보냅니다. ② 매월 점검에 "최고관리자 작업" 목록을 따로 두고 정보보호 담당자만 승인합니다. 최고관리자는 볼 수 있지만 승인하지 않습니다(화면을 감추지 않음). ③ 04 3장에 데이터 고침과 데이터베이스 직접 접근은 요청, 승인, 기록을 거친다고 적습니다. 표준 시각 맞추기와 덧붙이기만 되는 저장은 이미 있어 넣지 않습니다.
- **기획자 결정:** (2026-11-02, C-6) 최고관리자는 자기 작업이 든 점검을 승인하지 못함. 매월 점검에 "최고관리자 작업" 목록을 따로 두고 정보보호 담당자만 승인(4장 21번).
- **반영(v0.6, 2026-11-03):** ② SCR-57에 "최고관리자 작업" 목록(최고관리자 계정 모두의 그달 작업)과 정보보호(담당자, 리더)만 남기는 결과. 최고관리자는 자기 작업이 든 달의 매월 점검, 분기 검토, 자기에 대한 알림을 남기지 못하고, 다른 점검 화면에서도 자기 작업이 든 줄은 남기지 못함. 자기 작업이 든 달은 접속 기록이 한 줄이라도 있는 달 [가정](01 REQ-AUTH-14, REQ-ADM-18, REQ-ADM-20, 03 8-3장 `super_work_review`, 06 CTL-123).
- **반영(v0.4, 2026-11-01):** ① 세 기록의 지문을 잇고 매일 확인하며, 어긋나면 이상 행위 알림을 냄(01 REQ-SEC-06, 03 `prev_hash`, `row_hash`, `CODE-ALERT-KIND` `LOG_CHAIN`, 04 3장 "기록 지문 잇기"). ③ 데이터 직접 고침의 요청, 승인, 실행 기록(01 REQ-SEC-13, 03 `CODE-ADMIN-AREA` `DATA_FIX`, 04 3장 "데이터 직접 고침"). 서버 할 일이라 시안 화면은 그대로. 승인자는 그 업무의 리더와 정보보호 리더로 둠 [가정]. ②는 4장 21번 결정을 기다림.

### G-25 직접 입력한 거래처와 거래처 변경을 다른 사람이 보지 않고, 기능 목록에 회계 연결 정보가 없음
